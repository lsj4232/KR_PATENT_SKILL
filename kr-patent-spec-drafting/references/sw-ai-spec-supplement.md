# G 계열(AI, SW, 제어, 시스템) 명세서 보충 규범

`kr-patent-spec-drafting` SKILL.md의 **G 프로파일 부속 규범**이다.
SKILL.md 본문(S1~S7)이 정형 문구와 절대 원칙을 규정한다면, 이 문서는
**분량, 실시예 계층, 챕터 골격, 유형별 필수 서술 항목, 진행 게이트**를 규정한다.

출처: kr-spec-writing 통합본(2026-08-03) + 대표변리사 리뷰 원칙.

---

## 1. 입력 유형 자동 판별

| 입력 유형 | 처리 방식 |
|---|---|
| 구어체 텍스트 | 핵심 구성요소, 흐름 추출 후 구조화 |
| IDF, 기술설명서 | 청구항 후보, 실시예 후보 직접 추출 |
| 논문, 연구자료 | 기술적 기여(contribution) 중심 추출 |
| 미팅 녹취록 | 발명자 강조 축과 부정 축을 명시적으로 분리 추출 |
| 혼합 | 충돌 시 **발명자 의도 우선** |

발명 유형은 G1(AI/ML), G2(데이터 처리 SW), G3(제어), G4(시스템/네트워크),
G5(BM), G6(복합)으로 판별한다. 판별 결과는 S11 서두와 S13 챕터 구성에 반영한다.

---

## 2. 볼륨 강제 규칙 (V1~V7)

실체 서술이 충분한지 자가 점검하는 하한선이다. 하한 미달이면 **지원요건과
실시가능요건이 흔들린다**고 보고 보강한다.

| # | 규칙 |
|---|---|
| V1 | 실시예 본문: 최소 600문장 / 25,000자 / 30페이지 이상 (권장) |
| V2 | 4계층 실시예(L1~L4)를 모두 작성 |
| V3 | 【발명의 내용】 각 하위섹션: 최소 5문장 |
| V4 | 배경기술: 최소 3단락, 각 단락 5문장 |
| V5 | 종속항: 총 최소 8개 (권장 15~25개) |
| V6 | 보완 문단 삽입 시 반드시 15~25문장 (3문장 이하 금지) |
| V7 | 구성요소 1개당 최소 3회 서술 (정의 → 구체화 → 조건/변형) |

V6은 사후 보강(권리범위 보강 5단 사이클)에서 특히 중요하다. 짧은 문단 삽입은
심사 대응에서 근거로 쓰이지 못한다.

---

## 3. 실시예 4계층 (L1~L4)

가능한 모든 챕터에서 4계층을 다층 서술한다.

| 계층 | 성격 | 도입 문형 |
|---|---|---|
| **L1** 기본 실시예 | 핵심 흐름 통합 서술 | "일 실시 형태에 있어서, ~" |
| **L2** 변형 실시예 | 다른 예시 | "다른 예로서, ~할 수 있다." |
| **L3** 선택 실시예 | 조건부 분기 | "일 실시예에 따르면, ~경우에는 ~할 수 있다." |
| **L4** 대체 실시예 | 대안적 구성 | "추가적으로 또는 대안적으로, ~할 수 있다." |

L2~L4는 분할출원, 계속출원의 권리범위 베이스가 된다. 청구항으로 승격 가능한
수준까지 상세히 쓴다.

---

## 4. 챕터 목차 골격 (S12에서 수립)

큰 주제별로 【1. ○○】, 하위 주제는 【1A. ○○】 형식.

```
【1. 시스템 개요 및 전체 데이터 흐름】
  【1A. 시스템의 전체 구성】
  【1B. 이동형 장치의 상세 구성】
  【1C. 사용자 단말의 구성】

【2. 사용자 인터페이스의 서빙 및 접속 정보의 생성】
  【2A. 로컬 서버를 통한 사용자 인터페이스의 서빙】
  【2B. 접속 정보의 생성】
```

docx 출력 후 Word 탐색창 트리로 보이게 하려면 `kr-patent-navigation-pane`의
챕터 분할 기능을 사용한다.

**메인 흐름 설정**: 전체 발명을 가장 잘 대표하는 흐름도 또는 핵심 도면을
메인 실시예로 지정하고, 메인 도면의 단계를 설명할 때 다른 도면(블록도, 개념도,
세부도)을 연계하여 "메인 구조 + 구체 실시예" 구조로 쓴다.

**도면 그룹 구조**: 서브 도면 (a)~(n)이 있으면 각각을 실제 수행 절차의 단계로
해석하여 별도 문단으로 확장한다. 다만 서브 도면이 메인 도면의 단계 설명을 보조하는
예시 도면이면, 독립적인 "도 N을 참조하면" 단락을 만들지 않고 메인 도면 단계 설명
문단 내부에 예시로만 삽입한다.

## 5. 부재번호 원칙 (P1~P6, 대표변리사)

| # | 규칙 |
|---|---|
| P1 | 데이터 처리 흐름상 실제로 산출, 변환되는 **객체 단위**로 부여 |
| P2 | 직접 산출 객체와 후속 처리 객체를 **서로 다른 부재번호**로 구분 |
| P3 | 동일 객체는 명세서 전체에서 동일 부재번호로 일관 표기 |
| P4 | 추상적 용어 정의 단락(S11)에는 부재번호를 부여하지 않음 |
| P5 | 본문에서 객체가 실제 등장하는 단락에 최초 표기 |
| P6 | 중간 단계를 건너뛰어 표기하지 않음 |

의미 밴드: 100번대 하드웨어 구성, 200번대 사용자와 클라이언트, 300번대 데이터
처리 흐름상 산출 객체, 400번대 확장 및 부가 객체, S 단계는 방법 흐름도 단계.
설계는 `kr-patent-symbol-design`이 담당하며, S12에서 **각 챕터별로 어느 부재번호를
최초 도입할지 계획**을 세운다.

## 6. "상기" 사용 규칙 (대표변리사)

| # | 규칙 |
|---|---|
| S1 | 【발명을 실시하기 위한 구체적인 내용】 본문에서는 원칙적으로 "상기"를 쓰지 않는다 (부재번호로 구별 가능) |
| S2 | 예외 ① 도면부호가 없어 명확성 확보를 위해 필요한 경우 |
| S3 | 예외 ② 추상적 용어 정의 단락에서 청구항 용어를 받아 도입할 때의 "여기서, 상기 ~", "한편, 상기 ~" |
| S4 | 청구항에서는 "상기"를 그대로 유지 (S4 과제의 해결 수단 포함) |

## 7. 표현 정밀성 (E1~E4)

| # | 규칙 |
|---|---|
| E1 | "변환"은 **입력 객체 자체가 출력 객체로 바뀌는 경우만**. 입력에 기반해 별도 출력이 만들어지면 생성, 산출, 획득 |
| E2 | 부정만 기재 금지. (금지) "A, B, C 형태로 한정되지 않을 수 있다" → (권장) "A, B, C 형태로 표현될 수 있으나, 이에 한정되지 않을 수 있다" |
| E3 | 동의어 일관 (갱신/업데이트, 보정/교정 등 명세서 전체에서 하나로 통일) |
| E4 | 슬래시 표현 풀어쓰기 ("검증/교정" → "검증 및 교정") |

---

## 8. 유형별 특화 필수 서술 요건

정량 수치, 특정 제품명, 벤더명은 회피하되 **구조와 흐름은 구체적으로** 쓴다.

### G1 (AI/ML)
- 학습 데이터의 출처, 특징, 수집 방법, 전처리 파이프라인 (단계별)
- 모델 아키텍처 상세 (레이어 구성, 파라미터 규모, Attention 메커니즘, activation function, backbone)
- 학습 방법 (optimizer, loss function, learning rate schedule, epoch, batch size, regularization, early stopping)
- 추론(inference) 시 데이터 처리 흐름
- 입력-출력 관계 및 주요 상관관계
- 데이터 드리프트, concept drift 대응 및 일반화 전략

### G2 (데이터 처리 SW)
- 전체 시스템 구성 (클라이언트-서버, 클라우드, 온프레미스, 엣지)
- End-to-End 데이터 처리 파이프라인
- 모듈 간 데이터 흐름과 인터페이스 (API 스펙, 메시지 큐, 데이터 포맷)
- 하드웨어 요구사항 또는 실행 환경 (CPU/GPU, 메모리, OS, 라이브러리 계열)
- pseudocode 또는 단계별 알고리즘 흐름
- 에러 처리, 예외 상황 대응, scalability, 보안 (인증, 암호화, 프라이버시)

### G3 (제어)
- 센서 입력의 종류, 주기, 전처리
- 제어 판단의 근거 데이터와 판정 로직
- 제어 명령의 종류와 전달 경로
- 구동부의 실체 (모터, 조향, 브레이크 등)
- 제어 결과의 피드백 수신 및 후속 처리
- 안전 조건, 비상 정지, 페일세이프

### G4 (시스템/네트워크)
- 주체별 역할 (서버, 단말, 중계자)
- 통신 프로토콜과 채널
- 다중 세션, 병렬 처리, 브로드캐스트
- 인증과 권한
- 상태 동기화

## 9. 진행 방식 (승인 게이트)

단계별 승인 게이트로 진행한다. 게이트를 건너뛰면 후단에서 전면 재작성이 발생한다.

1. 입력 분석 및 진입점 확인 (청구항 확정 여부, 발명 유형, 자료 완비)
2. S1 명칭 + 기술분야 → 승인
3. S2 배경기술 → 승인
4. S3 해결과제 → 승인
5. S4 해결수단 → 승인 (**청구항 전수 1:1 매핑 게이트 통과 필수**)
6. S5 효과 → 승인
7. S6 실시예
   - S11 서두 → 승인
   - S12 도면 분석 및 목차 골격 → 승인
   - S13 챕터별 본문 (**챕터 단위 승인**)
   - S14 맺음말 → 승인
8. S7 최종 검토 → 승인
9. 부가 작성 (요약서, 대표도, 도면의 간단한 설명)

**진입점 규칙**

| 상황 | 진입점 |
|---|---|
| 청구항 확정, 명세서 미착수 | S1 |
| 명세서 일부 진행 중 | 해당 S 단계 이어서 |
| 명세서 초안 완성 | S7 검토 |

## 10. 미확보 자료 처리 (여백 처리)

발명자 측 자료가 미확보이면 **지어내지 않고 여백으로 남긴다.**

- 챕터 목차에 여백 챕터 표시: `【6. 사용자 인터페이스 관련 실시예】 〈자료 수령 후 확정〉`
- S4 해결수단, 도면 프롬프트, 요약서에서도 해당 부분 여백
- 자료 도착 시 여백 챕터를 채우고 관련 부분을 후속 조정

## 11. 부가 작성 세부

### 요약서
- 청구항 1의 실체를 압축 없이 담는 최소 규모 (약 200~350자)
- 청구항 1 문언을 그대로 가져와 **하나의 문장**으로 구성
- 시스템 청구항은 방법 청구항과 실체가 겹치므로 별도 서술하지 않고
  "및 이를 수행하는 [시스템 명칭]"으로 통합
- **프로그램 청구항(기록매체항)은 요약에 반영하지 않는다** (실무 관례)

### 대표도
- 시스템 전체 구성도 또는 방법 흐름도. 심사관과 제3자가 개요를 빠르게 파악할 도면

### 도면의 간단한 설명
- 각 도면의 문언을 **S13 본문 도면 도입 첫 문장의 "~이다" 부분과 정확히 일치**시킨다
- 부재번호는 도면의 간단한 설명 자체에는 표기하지 않는다

## 12. 산출물

명세서 초안 완성 후 다음을 함께 산출한다.

- 명세서 docx (`kr-patent-docx-builder`, 사무소 규격)
- 도면 프롬프트 (`patent-block-diagram` 또는 외부 생성 도구용)
- 도면부호 정리표
- 청구항, 명세서 정합성 자가 점검표 (`kr-patent-consistency-check`)
